# Three-pass imports

**Theory text (22 October 2026, user approved)**

Apply the [theory-text principles](booklet-cross-session-rules.md#theory-text-source-fidelity-and-cognitive-load-22-october-2026-user-approved) during authoring and the existing independent content review. Preserve source theory and taught methods; make only small, justified clarity improvements or necessary corrections. Do not expand an introduction with edge cases, duplicate a demonstration in prose or repeat shared instructions in its parts. Retain essential conditions, intermediate steps and useful accepted clarifications. Compare imported theory with the source and saved authorised changes, and record substantive departures with the original evidence retained. This adds no review stage, pedagogy pass or import hold, and does not renew historical acceptance.

Practice-question reasoning ratings are mandatory during initial authoring; follow the [LLM rating requirement](question-bank-assessment.md#llm-ratings-for-all-studio-practice-questions-21-october-2026). Use the existing content review to check rating consistency, retain actual model/task provenance and require complete verified coverage before delivery. This adds no review stage and excludes teaching examples and guided practice.

## Streamlined textbook imports (18 October 2026, user approved)

**ICE-EM continuation override (23 October 2026, user directed):** follow the actual Cambridge Extension 1 direct route: reuse inventory/source plans and accepted content, author missing work, inspect the early sample, independently review content, then save/export/check and inspect the targeted final pages. Do not add a mandatory polish pass or an autonomous diagnosis/evidence-request loop. Retain completed polish work. The main agent inspects failures directly and applies batched substantive repairs through existing revision-safe tools. All requested editions and applicable mathematical, source, diagram, rating and visual checks remain required. This overrides step 5’s added polish requirement for the remaining ICE-EM campaign.

Applies to work not yet started, including remaining textbook campaign work when its next process launches or a coordinator reaches a completed stage boundary. Do not interrupt active workers, invalidate their inputs, redo successful stages or rewrite historical evidence. This section supersedes conflicting mandatory stages elsewhere on this page.

1. Prepare source PDFs, original page images and answer keys once. In one independent source pass, produce a concise question coverage index together with exercise boundaries, cross-page continuations and teaching references. Include every question, part, mathematically necessary diagram, scaffold and embedded instruction. A short exclusion for a standalone teaching region or decorative illustration suffices; do not exhaustively describe decoration or transcribe reference-only teaching. Do not add a second model pass merely to organise an already usable index. Necessary recovery of invalid continuations, missing source context or genuine source defects remains scoped work.
2. Author editable questions, short answers, complete worked solutions and best-fit classifications together. Reuse compatible accepted content automatically. Use established house presets. Retrieve earlier teaching when needed for the assessed method; there is no separate teaching approval.
3. Inspect an early sample for new or difficult layouts. Reuse actual compatible inspections of proven ordinary layouts, without claiming the new pages were inspected. New figures, tables, fraction/scaffold layouts, custom arrangements, greater density or different rendering dependencies require a sample. Reuse existing sample files and reviews rather than adding pattern registers or evidence-rebinding scripts. Final automated and targeted visual checks still cover each chapter. The full-book review in step 5 compares teaching blocks with their source pages (23 October 2026), so a shared structural cause is found in the early sample and again at the end; see [the polish pipeline](booklet-verification-speed.md).
4. Run one independent content review of every new question and answer, including source fidelity, coverage, taught methods and skill mapping. Apply substantive corrections in batches; retain valid accepted mathematics. Run maths syntax, part-label, alignment and equals-gutter checks together at the completed content boundary. Only changed content or invalidated evidence returns to review.
5. Run `polish/run.mjs --textbook` (23 October 2026; default on, replaces `handoff/run.mjs`): the sweep and calibrated working space, wrapped-maths check, dependency ordering, the pagination optimiser with the orphan pull, the full-book first-pass review beside the source pages and its layout and content repairs, a residual review, and contact sheets of every Questions page; see [the polish pipeline](booklet-verification-speed.md). Textbook mode excludes pedagogy checks, challenges and suggestions. Then save revision-safely, export the requested editions, run automated checks on all of them and inspect the targeted final selection. Batch repairs; inspect repaired pages and neighbours once. Keep all five editions for ICE-EM; generating combined editions only on demand requires a separate user choice.
6. Deliver the Studio project, PDFs, substantive source corrections and genuine unresolved decisions in a short report. Prune regenerable export storage only after all import/repair/export processes finish, with preview then apply.

**No pedagogy review, pedagogy challenge, teaching-sequence redesign or pedagogy hold belongs to a textbook import.** Keep the standalone pedagogy tool available for explicit requests. Do not build source-teaching projections or wrappers to make textbook imports pass it. Preserve historical reviews; do not renew or delete them.

Do not add separate taxonomy reviews, repeated Studio reopen/readback rituals, broad closeout audits, extra receipts or scripts to re-record unchanged acceptance. Source/answer errors and print defects still need repair. Keep GPT-6.1 Sol low and the three-worker-per-booklet limit. Already completed ICE-EM inventories and valid source plans are reused, not regenerated under the shorter format.

Worker-limit precedence (6 October 2026): up to three workers per booklet, shared across sessions using that booklet's canonical run directory. Different booklets may each use three. Reuse the existing run for the same booklet; the lean multi-booklet dispatcher's `--concurrency` is per booklet. This supersedes older limits of three total across booklets and takes effect on the next dispatcher launch without disturbing active leases.

Applies only to new run manifests with `reviewProfile: "textbook-three-pass-v1"`. Never migrate a historical run implicitly. This profile takes precedence over older review-first and bounded-stage gate instructions; established source fidelity and editing conventions still apply.

Related: [lean import runtime](booklet-lean-import-runtime.md) covers `lean-import.mjs inventory|author|sample`, the shared worker pool and the frozen export. [Import duration controls](booklet-import-duration-controls.md) lists preparation checks and lessons from earlier imports. Both also describe the older ticket and queue route; where they differ from this page, this page governs new imports.

## Lean cut (5 October 2026, user-approved)

Measured on 38 recorded three-pass runs (28 September – 4 October): content review returned about 1,100 corrections that changed content and 1,070 that changed nothing or only review metadata; visual review found a real defect in 28% of batches; combined editions were 42% of visual batches with the same hit rate on the same page bodies; each booklet averaged 16 export runs and about 450 page inspections. The user does not need a system that catches one error in ten thousand. For new work:

- **Content review returns only real changes.** A correction changes printed content, an answer or a skill mapping. No identical-value patches and no patches that only record acceptance, evidence or review metadata; the reviewer's note is enough. The stage contract in `bounded-stages.mjs` now says this.
- **Visual review covers the standalone editions.** `student`, `short` and `worked` keep the targeted selection. Combined editions are selected only for covers, first and last pages, question/answer transitions and automatically flagged pages (`selectLeanVisualPages`). All five editions still get the automated checks.
- **After a visual repair, inspect only the repaired pages and their neighbours**, once. Do not re-queue pages whose content did not change, and do not inspect a page again because a hash, revision or export directory changed.
- **Three exports per booklet is the budget:** the early layout sample, the final five-edition export, and one re-export after the batched visual repairs. A further export needs a cause you can name; batch repairs so it is rarely needed.
- **No one-off bookkeeping scripts.** Do not write scripts to retain, rebind, re-register, reconcile or re-record evidence for content that did not change. If a guard blocks unchanged content, fix the guard once in the shared tool or report it; do not script around it per booklet. One-off content repair scripts stay in the run folder.
- **Finish with the short completion report** below. No receipts, closeout documents, readback or repeat-import checks, and no shading, visibility or bank audits for content those checks do not cover.

Still required: independent source inventory, the one independent content review of every item, the early layout sample, automated checks on all five editions, revision-safe saves, Sol 6.1 medium and at most three workers. Recorded runs keep the page selections already in their manifests; a new export applies the narrower combined-edition selection.

### Lean review route: no ledger (5 October 2026, user-approved)

New imports review and export through `scripts/booklet/lean-review.mjs` instead of the bounded-stage tickets, visual review queue, settlement and final-review records. It keeps three things under `RUN/lean-review/`:

1. **A revision-checked save.** A project in `booklets/projects/` is saved through `saveBookletProject` with its expected revision; a candidate file elsewhere is rewritten only while its bytes still match what the tool last read.
2. **One reviewed table**, `reviewed.json`: block ID → hash of its printable content and outcome; rendered page hash → inspection outcome.
3. **One correction log**, `corrections.jsonl`: every applied or rejected exact-field patch with its reason.

There are no tickets, ownership claims, renderer or teaching dependency hashes, evidence artifacts or settlement keys. A block is reviewed again only when its own printable content changes (layout, classification and review metadata do not count). A page is inspected again only when its rendered page hash changes. Over 38 recorded runs the ledger made about 737 state revisions per booklet and prompted roughly 430 one-off scripts to carry reviews forward; no record was found of it stopping a wrong answer or a broken page.

```text
node scripts/booklet/lean-review.mjs content --run-id RUN --project-file CANDIDATE.json
node scripts/booklet/lean-review.mjs export  --run-id RUN --project PROJECT_ID --project-file CANDIDATE.json --out .booklet-work/RUN/export-1 [--visibility-reviews FILE]
node scripts/booklet/lean-review.mjs visual  --run-id RUN --project-file CANDIDATE.json --exports .booklet-work/RUN/export-1
node scripts/booklet/lean-review.mjs status  --run-id RUN --project-file CANDIDATE.json [--exports .booklet-work/RUN/export-1]
node scripts/booklet/lean-review.mjs lint    --run-id RUN --project-file CANDIDATE.json
node scripts/booklet/lean-review.mjs repair  --run-id RUN --project-file CANDIDATE.json --corrections REPAIR.json [--exports .booklet-work/RUN/export-1]
```

### Automatic discovery before transcription (11 October 2026, user requested)

New prepared runs record `automaticReuse: true`. Before authoring, the importer searches earlier projects and their canonical review runs. It distinguishes the **original source block** from the **current improved editable version**. Text overlap retrieves candidates but never grants identity or acceptance. The author checks the whole original task/theory against the new source pixels, then carries compatible current clarifications, extra working and attached investigations. It returns a reuse reference rather than transcribing or solving the accepted content again. Local copying remaps IDs and mappings, removes prior bank/review status, and binds the copy to the new source and teaching pages. A changed given, assessed task or incompatible method cannot be silently carried as a clarification.

Content review finds acceptance automatically across projects. A current accepted version needs new-source, skill-mapping and taught-method checks, with no repeated derivation. When the editable version has changed but an earlier independently accepted version remains verifiable, the reviewer receives that baseline and the exact changed fields. It reviews only those amendments and their consequences. Completely new additions receive full review. Successful review retains the latest accepted snapshot and original source identity in the existing reviewed table; a later booklet can reuse that acceptance without rewriting the original master's old records. Pending or failed edits retain the earlier valid baseline; failure of that very same version revokes it. Saving never grants acceptance.

Studio's revision-safe save retains original-source lineage and links new blocks to their preceding original block through `sourceReview.additionTo`. The association survives later rearrangement. Existing supported block layout controls are captured and remapped with the copied content without invalidating mathematical acceptance. Earlier source-free additions immediately following an original block can also be discovered; ambiguous or independently sourced blocks are not guessed to be additions. The importer copies attached additions once with their anchor and records their intentional source departure. The most recently saved compatible version is preferred, so a newer audit is not replaced by an older accepted variant merely to avoid reviewing its changes.

The same scoped review applies when reviewing changed content in its own master run. Independent source/context checks still apply to every inherited item, and corrections can be accepted within the declared changed fields. A correction outside that scope, an incomplete compatibility check, changed task or missing baseline proof falls back to ordinary review. In-flight edits to the reused block, its acceptance or attached additions prevent stale reuse; unrelated project and review-row changes do not invalidate its proof. Source inventory and final layout/export checks remain required. This adds no model call or review stage, and measured time/token savings still require an actual comparable import.

Candidate retrieval verifies at most 36 shortlisted blocks and supplies up to 12 whole blocks and 16,000 characters per source page. Items outside that budget use ordinary authoring. Declared cross-page continuations and blocks requiring external image assets currently use ordinary authoring; editable native diagrams can be reused. Missing retained acceptance also uses ordinary authoring. Historical runs keep their existing prompts/caches; set `automaticReuse: true` in an existing run's author config only when intentionally enabling discovery for its incomplete authoring. `automaticReuse: false` in the author config disables discovery. Previous acceptance and historical evidence are never rewritten.

When a new source repeats accepted content, content review accepts optional paired inputs `--reuse-project PROJECT_ID_OR_JSON --reuse-run RUN_ID_OR_DIRECTORY`. Copies may record `sourceReview.reuse: {projectId, blockId}` to identify their prior block; otherwise a unique exact content match is required. Reuse compares questions, diagrams, teaching responses and both solutions while ignoring local IDs, question numbering, source references and layout. Mathematical colours remain significant. Prior acceptance must match current content and retain its independent review; legacy workflow records require current artifact bytes and their original dependency binding. An exact independently reviewed input snapshot can establish that only presentation changed. Missing, ambiguous or stale acceptance receives ordinary review.

The new independent reviewer still compares every reused item with the new source, teaching context and classification. It explicitly returns `sourceEquivalent`, `classificationVerified` and `taughtMethodEquivalent`; otherwise it completes ordinary mathematical review with `mathematicsReviewed: true`. Incomplete reuse falls back on the next content call. The existing reviewed table records the prior project/block, acceptance reference and reuse outcome. No prior run is rewritten and no live project or bank dependency is added.

- `content` sends every pending block to one independent Sol 6.1 medium reviewer, up to four consecutive blocks of a section per call and three calls at once, with the block's source page images and the topic's earlier teaching blocks. It applies the returned corrections inside the reviewed blocks, saves, and records each block as passed or failed. A correction whose `original` does not match is rejected and the block is reviewed once more, then marked failed for a person. Rerunning the command resumes; `--retry-failed` sends failed blocks again.
- `export` runs the existing five-edition draft export and automated checks in the frozen runtime, selects pages with `selectLeanVisualPages`, drops pages whose rendered hash is already accepted, and rasterises the rest into `visual-plan.json`.
- `visual` sends those pages to an independent visual reviewer, up to eight per call, records a per-page outcome and writes `visual-findings.json`. Repair the findings, export again and rerun `visual`: only pages that changed are inspected.
- Delivery needs `status --exports DIR` to report `deliverable: true`, or the remaining items listed for the user as unresolved decisions. With `--exports` the status counts only that export's pages, uses the export's own visual plan, lists its outstanding `findings`, and reports `exportProblems` when the checker did not pass there, an edition is missing or flagged, or the export was rendered from different project content.

Catching defects before the final export (added after the Compound Interest import, 5 October 2026, where eight final-export attempts followed defects that needed no rendering to find):

- **Lint first.** `lint` runs the existing pre-final text checks (`import-pre-final.mjs`) on the candidate. Unmatched or currency-paired `$` delimiters and maths that fails to render are blocking: `export` refuses to start while any remain, and `content` and `sample` report the counts. TeX-dot response scaffolds and unprinted layout-slot labels are listed for review and never block. Run `lint` on the first assembled chunk, not only on the finished candidate.
- **Sample a chunk that has answers.** `lean-import.mjs sample` renders `student`, `short` and `worked` when the candidate has practice content (student only otherwise, and says so). It returns lint, each edition's automated issues and the flagged pages with the sampled ones, and stays usable when the render fails: `ok: false` means repair and sample again before authoring more. Take the sample from the first assembled topic that includes an exercise, and carry what it finds into the instructions for the remaining pages. It is still the one early export.
- **One repair per visual round.** `repair` applies a file of exact-field patches (`{"corrections":[...]}`, the shape reviewers and repair workers return) through the revision-checked save and the correction log, so a repair needs no hand-written apply script. A patch targets a block or a node inside one, or `"targetId":"project"` for a field under `/settings` (answer-diagram widths live in `/settings/compactAnswers`). Nothing is saved if any patch fails to match; after saving, each value is read back and reported under `lost` if the save dropped it. With `--exports` it lists `findingsNotTouched`: repair those in the same round or record them as unresolved before exporting again. `visual-findings.json` holds every outstanding finding on the export, not only the last invocation's.
- **Concurrent skill-campaign writes.** An export no longer fails because `public/content/*.json` or `public/quizzes/*.json` for a skill the project never names changed while it ran; the receipt lists them under `unrelatedCampaignChanges`. Any other change under the frozen entries still fails the export. `export --resume-checked-export` reuses a passed export under the same rule, and `export --previous-exports DIR` limits the visual plan to pages whose hash changed since that export, with neighbours.
- **Launch failures.** If a worker dies within seconds without usage (for example Codex "Access is denied"), packet dispatch stops and the remaining pages keep their attempt number. Diagnose the environment, then run those pages again.

Trial on Percentages Problems (68-page student edition): 141 blocks formed 63 review batches; the export took 107 seconds with no automated issues and planned 85 page inspections in 14 batches, against 1,349 page inspections and nine final exports in its recorded run. The model calls themselves were not run in that trial.

Known trade-offs: a block is not re-reviewed when only a teaching example it relies on changes. A page hash covers the page's HTML and all project settings, so two repairs re-inspect a whole edition: one that changes the page count (every footer prints "Page N of M") and one that changes any setting, including a single answer-diagram width. Batch such repairs into one round. Inventory and authoring still register with the run's workflow file through `lean-import.mjs inventory|author`; `lean-import.mjs review|export|visual` and the bounded-stage commands remain for runs that already use them. Publishing questions to the bank through `import-project-bank.mjs` still expects its own verification records and is not part of this route.

### Pedagogy review before the final export (9 October 2026, user-approved)

Superseded for textbook imports by the 18 October 2026 rule above. The following is historical policy; it does not require a pedagogy call for unstarted textbook-import work.

After `content` reports nothing remaining and before the final export, run `node pedagogy/review.mjs review --project-file CANDIDATE.json` once; see [the pedagogy review](booklet-pedagogy-review.md#future-imports). It does not write the candidate. If it reports `holdBeforeFinalExport: true`, list the structural findings (repair type `reorder`, `add-question` or `add-teaching`) for the user with their block IDs and wait for the decision. Apply approved repairs through `repair`, let `content` review the changed blocks, then export. Otherwise go straight to the final export. Post the remaining findings as Studio comments only after delivery. Layout refinement that a structural decision could undo waits for that decision. This step adds no export and does not restore the separate teaching-approval or final-review passes.

## Passes

1. **Author.** Keep a concise source coverage checklist with stable references. Author editable questions, short answers, worked solutions and best-fit classifications together. Check a small sample of difficult layouts and fix shared causes before scaling up. No per-pattern approval register. Encode the source's [equation and working alignment](booklet-transcription-feedback-checklist.md#equation-and-working-alignment-4-october-2026) (position on the page, alignment between lines, worked-example question against working) while authoring; the content review checks it with the other source comparisons, and `check-dormant-alignment.mjs` should report nothing for the new project.
2. **Check and repair content.** One independent Sol 6.1 medium reviewer checks every teaching/practice item against the source and taught methods. Return scoped exact-field repairs in the review result and apply them through the existing correction log and revision-safe save. Batch related repairs. Missing rounding uses source/key precision, otherwise 2 decimal places when rounding is needed; preserve exact tasks. Choose taxonomy by source context and most advanced assessed skill. Only unresolved uncertainty with a material student-facing consequence blocks. Optional polish does not.
3. **Export, spot-check, deliver.** Once repairs settle, produce all five complete PDFs and their automated checks. Inspect the deduplicated selection: layout families and their densest examples, one ordinary page per exercise, covers, answer-section transitions, flagged pages and changed pages with neighbours. Rasterise only those pages, in range batches using at most two processes. No full pixel-comparison or footer-sheet requirement, and no further final pass after these checks pass.

New run configurations set `authoringPreferences: "house-presets-v1"` (4 October 2026). Author assignments then carry the preset-arrangement, templated-diagram and avatar guidance from `scripts/booklet/house-authoring.mjs`. A diagram in a supported family returns `diagramTemplate` parameters instead of code; the caller generates ordinary editable TikZ with `src/lib/diagram-templates.js` and keeps the parameters in `spec.template`. Speech-bubble characters return `{type:"image",avatar:"Name"}`; assembly assigns the standard avatars in booklet order. A custom arrangement records `sourceReview.customArrangement.reason`. The option is part of the author input hash, so recorded runs without it keep their prompts, caches and results. Every existing validator, diagram preflight and review still applies to the generated content.

> Scope note (9 October 2026): this paragraph and the two after it describe the ticket route. They apply to runs that already use bounded-stage tickets. New imports review and export through the [lean review route](#lean-review-route-no-ledger-5-october-2026-user-approved) above, which has no tickets or teaching bindings.

Use the existing `run-workflow next`, stage tickets and correction register. The new profile omits separate maths/theory/classification approval jobs and broad audit closeout gates. Resume accepted review results and export artifacts. A question/answer or relevant source/teaching edit invalidates its content review; taxonomy/review metadata and local layout edits do not. Printable edits invalidate relevant PDF editions and affected page inspections. Metadata edits rebind existing artifacts without printing. Before a third generation attempt record the cause and changed approach using `--regenerate-reason` (never merely repeat the failed command).

The first content assessment for a stable exercise may return `teachingSummary: {outcome: "accepted", sourceCompared: true, note, methods: [{statement, sourceRefs}]}` after actually inspecting all supplied teaching context. Existing assigned-source citation validation binds this summary to the final reviewed exercise context after the same result's repairs/resolutions and to the immutable result. Newly introduced teaching pages/artifacts that were not delivered to this reviewer cannot acquire acceptance through that binding. Later assessment batches reuse it only while its context hash, result and original source artifacts remain current; they still receive their own original question/key images and question-specific teaching notes. Changed source/context restores the original teaching evidence. This introduces no separate theory approval and accepts no additional questions. Record the first summary before dispatching subsequent batches for that exercise, so pending tickets keep their immutable bindings.

Later assigned question reviews may carry that summary forward across their own scoped decisions only when the complete source/method context remains identical and every additional artifact is from evidence delivered to that review or its actual result. Preserve the original summary and its artifact list; accumulating later review receipts as new question source dependencies would invalidate already checked content. Source or method changes still invalidate the summary.

The export report records pagination, diagram compilation, printing and selected image generation, plus actual reuse. These are measurements, not promised speed-ups. Retain original source evidence. Keep one correction log and one short completion report: deliverables, substantive corrections, genuine unresolved decisions and actual elapsed time. Do not create additional audit documents to unblock delivery.
## Occurrence-specific fill review in the lean table

`lean-review.mjs shading --run-id ID --project-file FILE --exports DIR` independently reviews native paint operations against their question context and current final-size PDF pages, without repeating accepted mathematics. Decisions stay in the existing reviewed table, bound to each occurrence, source hash and context hash. Run `check-diagram-shading.mjs --project FILE --lean-reviews RUN/lean-review/reviewed.json` for the same required fill-purpose gate; stale or incomplete decisions fail, and clarity fills require an actual outline-only comparison.
